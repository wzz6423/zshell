title: Working with AI agents
description: Let coding agents delegate work and coordinate across Zshell panes while you stay focused and in control.
---

Zshell's automation is primarily for AI coding agents. It gives them a safe way
to work with Zshell's panes and coordinate other agents; it is not another
command language you need to learn.

AI integration is enabled by default. Talk to your coding agent normally. It can create
a background pane, start a delegated worker, run a command, wait for the
result, and bring the answer back without taking focus from the pane you are
using.

## Wait for command results

For finite commands such as tests or a build, your agent can wait for the command’s own exit status and duration, then read saved recent terminal output. If a wait times out, the command keeps running and the same task can be waited on again. Waiting does not take focus. This requires an empty prompt in the original local zsh that Zshell launched; nested shells, SSH, and custom startup programs do not support command results. Recent terminal output can include earlier commands or prompts and is bounded, so ask the agent to save complete output to a file when needed.

Direct `exit`, `logout`, and `exec` are rejected because they end or replace the original shell; use `/bin/sh -c` for those commands in a subprocess.

## Setup

Check **Settings → Automation → AI**. It is on by default; if you previously
disabled it, enable it again, then start a new terminal or restart an agent
that was already running.

Zshell supports Codex, Claude Code, Gemini CLI, Grok Build, OpenCode, Cursor
Agent, Aider, Amp, and Pi. If Zshell finds an existing agent setup that conflicts
with this feature, it leaves that setup unchanged, returns the toggle to its
previous state, and shows the error in Settings.

## Ask in plain language

Tell your agent the outcome you want. For example:

> Run the focused tests in a background pane and tell me what fails.

> Delegate this bug to another Codex agent, then review its result.

> Ask the agent working on the API whether the schema is ready, then pass the
> answer to the agent running the tests.

> Start the dev server beside us, wait until it is ready, and give me the URL.

> Check whether the background agent is finished. If it is blocked, tell me
> what it needs.

The agent handles Zshell's automation interface on your behalf. You do not need
to type or memorize any Zshell automation commands.

## Let agents coordinate across panes

You can split related work across several Zshell panes and ask your main agent to
coordinate it. For example, one agent can work on an API while another updates
tests. The coordinating agent can ask a specific worker for its findings, send
a follow-up, pass the useful result to another worker, and bring the combined
answer back to you. The workers can use different supported coding tools.

This removes the copy-and-paste step from parallel work. Each agent keeps its
own conversation in its own pane, while the coordinating agent passes along
only the question, update, or result the other worker needs.

Sending a follow-up does not mean the work is finished. The coordinating agent
still waits for the worker, reads its result, and checks the outcome. A message
from another agent is also never treated as your approval. Permissions,
credentials, trust decisions, and destructive actions still come back to you.

## Keep working while it runs

Delegated panes stay in the background unless you ask to see them. When a
provider-native lifecycle integration reports state, Zshell shows it on the
agent's pane and tab:

| State | What it means for you |
| --- | --- |
| **Working** | The agent is actively handling the task. |
| **Blocked** | It needs input, approval, or another decision from you. |
| **Done** | It finished in the background and you have not viewed the pane yet. |

Zshell prefers native lifecycle events from Codex, Claude Code, Pi, OpenCode, and Grok, followed by explicit program reports. Hover the status badge or open **Agents** to see the source, waiting reason, percentage, and child tasks. Codex hooks must first be reviewed and trusted in its `/hooks` menu; Zshell does not bypass that review.

For recognized agent processes without a native report, Zshell can inspect a bounded live screen footer. **Screen inference** is labelled, never reports completion, never sends a notification, and cannot satisfy `zshell +agent wait`. It never grants an approval. Read the pane and verify the actual result before treating work as complete.

Programs can report progress with `zshell +agent report` and clear their own report with `zshell +agent clear`. Reports expire after 120 seconds without an update or when the owning process exits. See [program reports](#program-reports).

When an integration reports that an agent finished or needs input, Zshell can
also send a notification. Press <kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>A</kbd> to
jump to the next reported agent that needs your attention.

## Program reports [#program-reports]

A script or tool running inside a Zshell terminal can publish its own status:

```sh
zshell +agent report working --name Build --progress 25 --reason 'Compiling sources'
zshell +agent report blocked --name Build --attention approval --reason 'Review the release before publishing'
zshell +agent clear
```

`running` is an alias for `working`. `approval`, `input`, `login`, and `error`
are shortcuts for `blocked` with that attention reason. Other states are
`done`, `idle`, and `unknown`. `done` is an explicit status report, not a verified
command result. Zshell never answers a prompt or grants approval based on a report.
Completion in the focused pane is already seen, so `done` appears as `idle`
with its progress and task details retained. Reading through the API does not
mark a background completion seen; focusing that pane does.

For several child tasks, pass `--tasks` with a JSON array or send one JSON object
to `zshell +agent report --json` on standard input:

```json
{
  "name": "Build",
  "state": "working",
  "progress": 50,
  "tasks": [
    { "id": "compile", "title": "Compile", "state": "done", "progress": 100 },
    { "id": "tests", "title": "Tests", "state": "working", "progress": 20 }
  ]
}
```

Each report replaces the previous program report and child-task list. Task IDs
must be unique. A blocked child brings the parent to attention; an active child
keeps a reported idle or completed parent working. Percentages must be integers from 0 to 100. A report supports
at most 32 tasks; the badge tooltip previews eight and reports the total, while
`zshell +agent get --current` returns every task. Names are limited to 128 UTF-8
bytes, reasons to 1 KiB, task IDs to 128 bytes, task titles to 256 bytes, and
standard-input JSON to 32 KiB. Text must fit on one line and contain no terminal
control characters. Reports are limited to 10 updates per second per terminal.

The CLI binds the report to its parent process by default. `--pid PID` (or
`process_id` in JSON) may select a live ancestor of the CLI within the same
terminal. Its PID and process start time must still match. Refresh long-running
reports at least once every 120 seconds. Closing the terminal, exiting the owner,
or letting the report expire removes its status. `clear` removes only the
program report; it cannot clear a provider's native lifecycle state.

This interface uses Zshell's private, authenticated Unix socket and works with
both Ghostty and Alacritty. It has no pane or project target option. Printing
terminal text or an OSC sequence cannot impersonate a native lifecycle report.
Native state takes priority over program reports; inferred screen state is
lower priority and never counts as a result or approval.

## Account usage and limits

**Settings → Automation → Account Usage** shows available account limits for
Claude Code and Codex, including the used percentage, reset time when reported,
and the time of the last update. Use **Refresh Usage** to reload the latest
available data.

Codex needs an installed, signed-in CLI that can report account limits. Claude
Code usage appears when Zshell has received a status-line usage report from
the provider. The section only appears when usage data is available;
supported windows depend on the provider and account. These are account limits,
not a token total for the focused session.

## A typical workflow

1. Start your usual coding agent in a Zshell terminal.
2. Ask it to delegate a bounded task, run something in the background, or
   coordinate another agent.
3. Continue working in your current pane while Zshell keeps the delegated work
   visible in the project layout.
4. Follow a provider-reported **Working**, **Blocked**, or **Done** badge when
   available. If the tool does not report lifecycle, open the pane to inspect
   its conversation or terminal output instead.
5. Review the resulting files in the [Git panel](/en/docs/git), inspect the diff,
   and decide what to keep.

## You stay in control

- Agent automation stays inside the current Zshell project and cannot reach
  panes in another project or window.
- Background work does not take focus unless you explicitly ask for it.
- Zshell never answers permission, credential, trust, or destructive-action
  prompts for you. A provider-reported blocked agent hands that decision back
  to you.
- Reported completion is a signal to review the result, not an automatic
  approval of the agent's changes.

## If an agent does not use Zshell

- Confirm that **Settings → Automation → AI** is enabled.
- Open a new Zshell terminal if the current one existed before you enabled the
  setting.
- Restart an agent that was already running when you enabled it.
- Check Settings for an inline setup error.
- Ask explicitly for a "background Zshell pane" or a "delegated Zshell agent" if
  you want the agent to use this workflow for a task.

## Resume the original conversation

With **Resume agent conversations** enabled, reopening a terminal pane resumes its recorded Claude Code, Codex, Pi, or OpenCode conversation when the original PTY is unavailable. The conversation belongs to that pane, even when several panes use the same directory.

Zshell installs SessionStart hooks for Claude Code and Codex, a Pi extension, and an OpenCode TUI plugin in existing provider configuration. Your other hooks, plugins, settings, and JSONC comments are preserved. Enable the hooks in Claude Code’s trust prompt and approve new Codex hooks in `/hooks` when the provider asks. Restart an agent that was running before installation.

Only local root conversations reported by these integrations can be resumed. Codex requires an embedded local CLI (`--no-daemon`); shared daemons and remote connections are unsupported. OpenCode requires the TUI plugin API; older versions, headless server sessions, and `opencode attach` are unsupported. A child agent cannot replace the parent pane’s conversation. Pi requires its saved session file.

No verified identity, a missing working directory, or an unavailable Pi file opens a new shell. An unavailable CLI also returns to a shell. Zshell does not replay an arbitrary startup command or pick a recent conversation. Provider errors such as a deleted conversation are displayed by the CLI.
